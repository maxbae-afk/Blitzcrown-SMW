# 프레임 시퀀스

**스크롤 시퀀스는 넓은 화면 전용입니다.** 900px 이하에서는 시퀀스를 한 장도 받지 않고
세로 슬라이드 롤링(reel)으로 대체합니다. 아래 [모바일](#모바일--슬라이드-롤링) 참고.

시퀀스는 세 개가 이어 붙어 있습니다.

| id | 내용 | 장수 / 용량 | 이동 거리 | 프레임당 |
| --- | --- | --- | --- | --- |
| `main` | 코인 → 성 → 딜러 → 이륙 | 264장 / 19.7MB | 1012vh | 3.83vh |
| `bridge` | 프로펠러기 순항 (다리) | 22장 / 2.6MB | 77vh | 3.50vh |
| `ascent` | 폭발 → 제트 전환 → 우주 | 144장 / 10.8MB | 552vh | 3.83vh |

"이동 거리" 는 그 시퀀스가 재생되는 동안 실제로 굴러가는 스크롤입니다
(`styles.css` 의 `--travel-*`). 구간 자의 높이는 여기에 화면 하나를 더한 값입니다.

머무는 거리까지 더한 페이지 전체 스크롤은 1796vh, 총 430장 / 33.0MB 입니다.

`manifest.json` 이 없거나 첫 프레임을 못 읽으면 페이지는 절차적 씬으로 자동 폴백합니다.

## 폴더 구조

```
blitzcrown-v2/
├─ _source-frames/          ← main   PNG 원본 1920×1080 264장 (배포 대상 아님)
├─ _source-frames-bridge/   ← bridge PNG 원본 1920×1080  22장 (배포 대상 아님)
├─ _source-frames-2/        ← ascent PNG 원본 1920×1080 144장 (배포 대상 아님)
├─ _source-reel/            ← 모바일 슬라이드 PNG 1290×2796 6장 (배포 대상 아님)
├─ .tools/
│  ├─ convert.mjs           ← 이미지 변환 + manifest 생성
│  ├─ reel.mjs              ← 모바일 슬라이드 변환
│  ├─ encode-sweep.mjs      ← 화질 유지하며 줄일 여지 측정 (effort·서브샘플링)
│  ├─ grade.mjs             ← 컬러 그레이딩 (변환 단계에서 구움)
│  ├─ pacing.mjs            ← 시퀀스·구간 정의와 페이싱 계산 (convert/repacing 공용)
│  ├─ repacing.mjs          ← 재인코딩 없이 페이싱만 갱신
│  ├─ pace-profile.mjs      ← 구간별 프레임당 vh + 이음매 속도차 (브라우저 불필요)
│  ├─ chapter-map.mjs       ← 프레임 번호 → 챕터 data-start/end 환산
│  ├─ contact-sheet.mjs     ← 썸네일 시트 (프레임 번호 포함)
│  ├─ boundary.mjs          ← 맞닿는 시퀀스의 끝/첫 프레임 비교
│  ├─ color-check.mjs       ← 이음매 앞뒤 색 비교 (원본 vs 변환)
│  ├─ match-fit.mjs         ← 시퀀스별 클립 맞추기 계수 산출
│  ├─ payload.mjs           ← 세트별 장수와 실제 용량
│  ├─ analyze-color.mjs     ← 원본 색 분포 측정
│  ├─ preview-grade.mjs     ← 그레이딩 전/후 비교 이미지
│  ├─ quality-sweep.mjs     ← 인코딩 설정별 화질/용량 측정
│  ├─ decode-bench.mjs      ← WebP vs AVIF 디코딩 속도 측정
│  ├─ serve.mjs             ← 로컬 정적 서버 (127.0.0.1:4321)
│  ├─ page.mjs              ← 브라우저 도구 공용 (띄우기·대기·스크롤·상태 읽기)
│  ├─ scan.mjs              ← 브라우저에서 실제 재생 속도 측정
│  ├─ verify.mjs            ← 전 구간 재생 + 구간 자 이음새 검증
│  ├─ seam-check.mjs        ← 이음매 교차 구간 촬영
│  ├─ hold-check.mjs        ← 프레임 번호가 멈춰 있는 구간 측정
│  ├─ motion-check.mjs      ← 화면이 실제로 안 움직이는 구간 측정
│  ├─ copy-check.mjs        ← 챕터 카피별 노출 구간 측정
│  └─ mobile-check.mjs      ← 모바일 롤링 검증
└─ srolling/frames/
   ├─ manifest.json
   ├─ main/    desktop/  frame_0001.avif … frame_0264.avif   (19.7MB / 평균 76KB)
   ├─ bridge/  desktop/  frame_0001.avif … frame_0022.avif   ( 2.6MB / 평균 122KB)
   ├─ ascent/  desktop/  frame_0001.avif … frame_0144.avif   (10.8MB / 평균 76KB)
   └─ reel/              slide-1-860.avif … slide-6-1290.avif (0.7MB / 모바일 전용)
```

> 원본 PNG 는 반드시 `_source-*` 에 둡니다. `srolling/frames/<id>/` 는 `convert.mjs`
> 가 매번 비우고 다시 쓰는 출력 폴더라, 여기에 원본을 넣으면 다음 변환 때 사라집니다.

원본이 2560px 이상이면 `retina/` 세트가 하나 더 생성되고, 캔버스가 2200px 넘게 요구하는
화면에서 자동으로 선택됩니다. 현재 원본은 1920이라 생성되지 않습니다.

`jobs` 에서 빠진 세트가 디스크에 남아 있으면 `convert.mjs` 가 지웁니다. 매니페스트에는
안 적히지만 용량은 그대로 차지하기 때문입니다.

## 시퀀스가 이어지는 방식

맞닿는 프레임끼리 거의 같은 컷입니다(`boundary.mjs` 로 잰 평균 밝기차 1.3 / 2.7 · 255).
그래서 섹션을 나누지 않고 **sticky 화면 하나를 공유**합니다.

```
<section class="scene-stack">        ← 세 시퀀스의 이동 거리를 합친 높이
  <i id="scene">   …                 ← main 구간을 재는 눈에 안 보이는 자
  <i id="scene2">  …                 ← bridge 구간
  <i id="scene3">  …                 ← ascent 구간
  <div class="scene-sticky">         ← 화면. 여기서만 계속 고정된다
    <canvas id="sceneCanvas">        ← main  (항상 깔려 있다)
    <canvas id="sceneCanvas2">       ← bridge (이음매에서 opacity 0 → 1)
    <canvas id="sceneCanvas3">       ← ascent (그 위에 한 번 더)
```

섹션을 나누면 앞 섹션의 sticky 가 풀려 올라가는 동안 뒤 섹션이 아래에서 올라와,
화면이 위아래로 갈라지는 전환이 그대로 보입니다. 같은 컷이 이어지는 구간에서는 눈에 띕니다.

`app.js` 는 각 구간 자의 시작선이 화면 위로 `SEAM_PX`(24px)만큼 지나가는 동안
그 캔버스의 `opacity` 를 0 → 1 로 올립니다. 뒤 캔버스일수록 위에 겹쳐 두었으므로
순서대로 덮이면서 넘어갑니다.

**이 값은 짧아야 합니다.** 시퀀스끼리는 이어지는 컷이지 겹치는 컷이 아닙니다. 앞 시퀀스는
자기 구간이 끝나는 지점에서 이미 마지막 프레임에 도달해 멈추므로, 교차하는 동안 화면을 덮고
있는 건 멈춘 그림입니다. 교차를 길게 잡으면 그 길이만큼 그대로 정지 구간이 됩니다.

180px 였을 때 이음매마다 90px 씩(마우스 휠 한 칸 분량) 그림이 멈춰 있었고, 비행 구간에서
스크롤이 걸리는 느낌으로 나타났습니다. 24px 로 줄이자 프레임 하나가 머무는 정상 거리(약 32px)
안으로 들어왔습니다.

가려 줄 것이 없다는 근거는 `boundary.mjs` 가 냅니다. 경계를 넘는 그림 차이가 같은 클립 안
이웃 프레임 사이의 차이보다 작습니다(0.36x · 1.19x). 즉 넘어가는 순간이 평범한 프레임 진행과
구별되지 않습니다. 경계가 튄다면 이 값을 늘릴 게 아니라 클립 맞추기(`match`)로 잡으세요.

시퀀스를 늘리려면 `app.js` 의 `SEQUENCES` 배열, `styles.css` 의 `--travel-*` 와
`#scene*` 규칙, `index.html` 의 자·캔버스를 한 줄씩 늘리면 됩니다.

### 계기판은 한 벌

시퀀스마다 계기판을 두면 이음매에서 두 벌의 숫자가 같은 자리에 겹쳐 읽힙니다.
그래서 `#hud` / `#rail` 은 하나만 두고, 지금 화면을 덮고 있는 시퀀스(교차가 절반을 넘긴
것 중 가장 뒤엣것)의 숫자를 씁니다. `SEQUENCE` 칸이 어느 시퀀스인지 알려 줍니다.
레일만은 전체를 가로지르는 눈금이라 이음매에서 0으로 되돌아가지 않습니다.

진단 도구가 시퀀스별 숫자를 따로 봐야 하므로, `app.js` 가 `window.__sequence` 로
상태를 열어 둡니다. 페이지 동작은 여기에 의존하지 않습니다.

### 카피는 이어 붙인 하나의 타임라인

챕터 카피는 교차에 관여하지 않습니다. 컨테이너 `#chapters` 하나에 모아 두고,
**세 시퀀스의 진행도를 더한 0~3 값**으로 재생합니다.

```
0.000 ────────── 1.000 ── 2.000 ────────── 3.000
     main         bridge        ascent
```

앞이 1에 닿는 지점에서 다음이 0부터 시작하므로 합이 그대로 연속된 값이 됩니다.
덕분에 `05 / TAKE OFF` 는 `data-start="0.837" data-end="2.231"` 로 두 이음매를 모두
가로질러 1.33화면 동안 계속 떠 있습니다.
컨테이너를 시퀀스별로 나누면 그 카피가 이음매에서 한 번 사라졌다 다시 나타납니다.

노출 구간은 이렇게 확인합니다.

```bash
bun run copy-check.mjs
```

### 구간 자의 위치 — 화면 하나만큼 당겨야 한다

구간 자 하나가 실제로 소비하는 스크롤은 `height − 100vh` 입니다.
진행도가 1에 닿는 지점이 자의 아래 끝에서 **한 화면 위**이기 때문입니다.

그래서 CSS 변수는 자의 높이가 아니라 **이동 거리**(`--travel-*`)로 두고,
높이 쪽에 화면 하나를 더합니다. 다음 자는 이동 거리만큼만 내려가 시작합니다.

```
#scene   top 0                              height  --travel-main   + 100vh
#scene2  top  --travel-main                 height  --travel-bridge + 100vh
#scene3  top  --travel-main + --travel-bridge   height  --travel-ascent + 100vh + --end-hold
```

`− 100vh` 에 해당하는 이 당김을 빼먹으면 시퀀스 사이에 화면 하나만큼(900px) 프레임이
완전히 멈춘 구간이 생깁니다. 스크롤은 하는데 그림이 그대로라 눈에 바로 띕니다.
`verify.mjs` 가 자끼리의 어긋남을 px 로 찍어 주므로 0인지 확인하면 됩니다.

멈춤 구간은 두 가지로 잴 수 있습니다. 교차 중에는 어느 쪽 프레임 번호를 봐야 할지
알 수 없으므로, 체감을 확인할 때는 화면 픽셀을 직접 비교하는 `motion-check.mjs` 쪽이 정확합니다.

```bash
bun run hold-check.mjs      # 프레임 번호 기준
bun run motion-check.mjs    # 스크린샷 변화량 기준 (정지 구간 그대로 드러남)
```

### 머무는 거리

`--end-hold` (55vh · 모바일 42vh) 하나뿐입니다. **마지막 시퀀스가 끝난 뒤**
다음 섹션으로 넘어가기 전의 여운입니다. 엔진이 `getComputedStyle(구간 자).--end-hold`
를 읽으므로, 앞쪽 자들에는 `--end-hold: 0vh` 를 덮어써서 곧바로 다음으로 넘깁니다.

시퀀스와 시퀀스 **사이에는 머무는 거리를 두지 않습니다.** 앞 시퀀스의 마지막 컷이 뒤
시퀀스로 그대로 이어지므로, 여기에 값을 주면 같은 그림에서 스크롤만 정체됩니다.
전에 18vh(162px)를 뒀다가 "스크롤이 걸린다" 는 지적을 받고 걷어냈습니다.
장면이 확실히 끊기는 시퀀스를 붙일 때만 다시 고려하세요.

교차 구간이 의도대로 나오는지는 이렇게 확인합니다.

```bash
bun run serve.mjs        # 별도 터미널
bun run seam-check.mjs   # 이음매마다 shots/seam-1-scroll.png, seam-2-scroll.png
```

### 로딩 순서

첫 시퀀스만 부팅을 붙잡고, 나머지는 배경에서 **순서대로 하나씩** 받습니다.
`bridge` 는 `main` 의 배경 로딩이 끝난 뒤에, `ascent` 는 `bridge` 가 끝난 뒤에 시작합니다.
동시에 받으면 대역폭을 나눠 쓰다가 먼저 필요한 쪽이 늦게 도착하고,
아직 빈 자리는 가장 가까운 프레임으로 때워져 엉뚱한 컷에서 멈춘 것처럼 보입니다.

## 시퀀스 교체 방법

장수는 자유롭게 바꿔도 됩니다. 변환 스크립트가 원본을 세어 `manifest.json` 까지 다시 씁니다.

1. After Effects에서 **1920×1080 · PNG 시퀀스** 로 렌더합니다. (24fps 기준 264장 ≈ 11초)
   AE의 JPEG 출력은 품질 제어가 거칠어 마스터로 쓰지 않습니다.
2. 해당 시퀀스의 원본 폴더를 비우고 새 원본을 넣습니다.
   파일명은 자유이며 **끝에 붙은 숫자 순서**로 정렬합니다. (`shot_1.png` → `shot_10.png` 도 정상 정렬)
   확장자는 png · jpg · webp · tif 를 받습니다.
3. `pacing.mjs` 의 해당 `SECTIONS` 를 새 컷 경계에 맞게 고칩니다.
4. 변환을 실행합니다.

```bash
cd blitzcrown-v2/.tools
bun run convert.mjs           # 전체
bun run convert.mjs ascent    # 한 시퀀스만 (나머지 manifest 항목은 그대로)
```

스크립트가 해당 시퀀스의 출력 폴더를 비우고 다시 쓰므로, 장수가 줄어도 이전 프레임이
남아 섞이지 않습니다. `manifest.json` 의 `count` 도 자동 갱신됩니다.

5. 컷 전환점이 달라졌으므로 `index.html` 의 챕터 `data-start` / `data-end` 를 새 영상에 맞춥니다.
   `chapter-map.mjs` 가 프레임 번호를 진행도로 환산해 줍니다.
   장수를 크게 바꿨다면 `styles.css` 의 `--travel-*` (이동 거리)도 프레임 수에 비례하도록
   조정하세요. 이음매에서 속도가 튀지 않으려면 **시퀀스 평균이 아니라, 이음매에 맞닿은
   두 구간의 프레임당 vh** 가 비슷해야 합니다. 구간마다 speed 배수가 다르므로 평균이
   같아도 경계에서 튈 수 있습니다.

```bash
bun run pace-profile.mjs
# ...
# 이음매 main → bridge: 비행 3.53vh → 전환 3.50vh  (-1%)
# 이음매 bridge → ascent: 전환 3.50vh → 편대 비행 3.45vh  (-1%)
```

`--travel-*` 는 자의 높이가 아니라 순수 이동 거리라 장수로 나누면 프레임당 거리가
바로 나옵니다. 모바일 값에도 **같은 비율**을 걸어야 합니다. 하나만 따로 줄이면
그 경계에서만 갑자기 빨라집니다.

## 시퀀스 새로 붙이기

`pacing.mjs` 의 `SEQUENCES` 에 한 줄 추가하면 변환·페이싱 도구가 모두 따라옵니다.

```js
export const SEQUENCES = [
  { id: 'main',   src: '_source-frames',        out: 'desktop', sections: MAIN_SECTIONS },
  { id: 'bridge', src: '_source-frames-bridge', out: 'bridge',  sections: BRIDGE_SECTIONS },
  { id: 'ascent', src: '_source-frames-2',      out: 'ascent',  sections: ASCENT_SECTIONS },
];
```

붙이기 전에 맞닿는 프레임이 같은 구도인지 먼저 봅니다. 밝기차가 10을 넘으면 교차가
디졸브로 보입니다.

```bash
bun run boundary.mjs     # shots/boundary.png + 경계별 밝기차 (변환 결과 기준)
bun run color-check.mjs  # 톤이 다른 클립인지 확인
```

구도가 같은데 밝기차가 남으면 원본 렌더의 톤이 다른 것입니다. 「클립 맞추기」 항목으로 잡습니다.

페이지 쪽은 세 군데를 한 줄씩 늘립니다.

1. `index.html` — `.scene-stack` 안에 구간 자(`<i class="scene-range" id="scene4">`)와
   캔버스(`<canvas class="scene-canvas scene-canvas--over" id="sceneCanvas4">`) 추가.
   캔버스는 **뒤 시퀀스일수록 뒤에** 놓아야 위에 겹칩니다. 계기판은 늘리지 않습니다.
2. `styles.css` — `--travel-<id>` 를 추가하고 `.scene-stack` 높이와 `#scene4` 의
   `top`/`height` 지정 (위의 "구간 자의 위치" 참고). 앞쪽 자에 `--end-hold: 0vh` 유지.
3. `app.js` — `SEQUENCES` 배열에 한 줄. 엔진 연결과 순차 로딩은 배열을 따라 자동입니다.

챕터 타임라인의 끝값(`createChapters` 의 `max`)도 시퀀스 개수를 따라가므로,
기존 카피의 `data-start`/`data-end` 는 `chapter-map.mjs` 출력으로 다시 옮겨 적습니다.

## 모바일 — 슬라이드 롤링

900px 이하에서는 스크롤 시퀀스를 **아예 구동하지 않습니다.** 이유는 두 가지입니다.

- 세로 화면에서 16:9 프레임을 채우면(`object-fit: cover`) 좌우가 통째로 잘려 나갑니다.
  1920×1080 을 390×844 화면에 맞추면 가로 500px 남짓만 남아서 장면을 알아볼 수 없습니다.
- 430장 33MB 를 모바일 회선에 지울 이유가 없습니다.

대신 세로로 따로 만든 6장을 텍스트와 함께 자동으로 넘깁니다.

| | |
| --- | --- |
| 원본 | `_source-reel/slide-1.png` … `slide-6.png` · **1290×2796** PNG |
| 결과 | `frames/reel/slide-N-{860,1290}.avif` · 합계 약 0.7MB |
| 한 장 머무는 시간 | 5.2초 (`reel.js` 의 `HOLD`) |
| 조작 | 좌우 스와이프. 화면 밖이거나 탭이 가려지면 멈춤 |

```bash
bun run reel.mjs                 # _source-reel/ 을 굽는다
bun run reel.mjs --placeholder   # 원본이 오기 전 기존 프레임으로 임시 채우기
bun run mobile-check.mjs         # 동작 확인
```

원본 이미지를 만들 때 지켜야 할 것:

- **글자를 그려 넣지 마세요.** 카피는 HTML 로 얹습니다. 이미지에 구우면 크기 대응도 안 되고
  나중에 문구를 못 바꿉니다.
- 아래 35% 는 어두운 그라데이션이 덮이고 그 위에 글이 올라갑니다. 중요한 것을 두지 마세요.
- 기기마다 세로 비율이 달라 위아래가 조금씩 잘립니다. 핵심 피사체는 세로 중앙
  **1290×2280** 안에 두세요.

### 두 경계가 같아야 합니다

`styles.css` 의 `@media (max-width: 900px)` 와 `app.js` 의 `compact` 가 같은 값을 봅니다.
한쪽만 고치면 **아무것도 안 보이거나(둘 다 숨김) 430장을 헛되이 내려받습니다**(둘 다 구동).

### 데스크톱이 슬라이드를 받지 않는 이유

슬라이드는 `<picture>` + `<source media="(max-width: 900px)">` 로 감쌉니다.
`display: none` 은 이미지 다운로드를 막지 못하기 때문에, 그냥 `<img src>` 로 두면
데스크톱도 이 6장을 그대로 받습니다. 조건이 맞지 않으면 `<img>` 에 src 가 없는 상태가 되어
요청 자체가 나가지 않습니다. `mobile-check.mjs` 와 `verify.mjs` 가 양쪽을 다 확인합니다.

### AVIF 한 벌만 굽는 이유

예전에는 WebP 를 함께 구웠습니다. AVIF 를 못 읽는 사파리 16.4 미만(2023년 3월 이전)
대비책이었는데, **AVIF 를 읽는 브라우저는 WebP 파일을 한 장도 내려받지 않습니다.**
사용자 다운로드에는 아무 보탬이 없으면서 저장 공간만 45MB 를 쓰고 있어서 걷어냈습니다.

되살리려면 `convert.mjs` 의 `formats` 배열에 webp 항목을 다시 넣으면 됩니다. 재생 쪽은
첫 프레임을 순서대로 받아 보고 성공하는 포맷을 채택하므로 코드를 고칠 필요가 없습니다.

### 클립 맞추기 (시퀀스별)

위 그레이딩은 **모든 시퀀스에 똑같이** 걸리는 look 입니다. 그래서 원본 렌더의 톤이 시퀀스마다
다르면 그 차이가 그대로 남고, 채도·대비 때문에 오히려 벌어집니다. 이음매에서 화면이 한 번
꺼졌다 돌아오는 것처럼 보이면 이걸 의심하세요.

실제로 bridge 원본은 다른 두 시퀀스보다 그림자가 눌린 채로 렌더돼서, 경계에서 평균 밝기가
한 프레임 만에 7.6 떨어졌다가 7.5 올라왔습니다. 클립 안에서의 변동은 ±0.3 이므로 25배입니다.

그래서 공용 look **앞에** 시퀀스별 정규화 단계를 둡니다. 순서가 중요합니다. 출발점을 먼저
맞춰 놓아야 같은 look 이 같은 결과를 냅니다.

```
리사이즈 → 샤프닝 → 클립 맞추기(match) → 공용 그레이딩 → 인코딩
```

계수는 이웃 시퀀스의 경계 프레임을 기준으로 뽑습니다. 경계에서는 앞뒤가 같은 구도라
두 클립의 화면 통계를 직접 견줄 수 있습니다. 평균만 맞추면 밝기는 맞아도 대비가 틀어지므로
어두운 쪽(p20)과 밝은 쪽(p80) 두 지점을 함께 맞춰 게인과 리프트를 동시에 풉니다.

```bash

bun run convert.mjs bridge     # 해당 시퀀스만 다시 변환
bun run color-check.mjs        # 이음매 앞뒤 색 비교 (원본/변환 함께)
```

출력된 값을 `pacing.mjs` 의 해당 시퀀스에 넣습니다.

```js

```

톤이 처음부터 맞는 시퀀스는 `match` 를 아예 두지 않습니다. 필요 없는 보정을 걸 이유가 없습니다.

## 구간별 재생 속도 (페이싱)

`manifest.json` 의 `pacing` 배열은 "몇 번 프레임이 스크롤 어디에 놓이는지"를 담은 누적 분포입니다.
어떤 프레임에 스크롤을 많이 배분하면 그 구간은 천천히, 적게 배분하면 빠르게 지나갑니다.

가중치는 두 단계로 만들어집니다.

1. **자동** — 프레임 간 실제 변화량을 재서, 구간 **안에서** 움직임이 큰 프레임에 더 배분합니다.
   덜컹거림을 줄이는 미세 조정 역할입니다. `PACING_STRENGTH` 로 강도를 조절하며 기본값은 `0.5`,
   `0` 이면 구간 안에서도 완전 균일해집니다.
2. **수동** — 구간 **전체**의 길이를 연출 의도대로 정합니다. 이쪽이 최종 결정권을 가집니다.

자동 가중치는 구간마다 평균이 1이 되도록 정규화됩니다. 이 과정이 없으면 움직임이 적은 구간은
"느리게" 로 지정해도 자동 가중치에 눌려 평범한 속도가 되어 버립니다.

### 속도 바꾸기

`.tools/pacing.mjs` 의 `MAIN_SECTIONS` / `BRIDGE_SECTIONS` / `ASCENT_SECTIONS` 를 고칩니다.
프레임 번호는 **시퀀스별 0-based 원본 기준**이고, `speed` 가 1보다 크면 느리게,
작으면 빠르게 지나갑니다. `speed` 를 적지 않으면 1로 둡니다.

```js
{ name: '동전 폭발', from: 8, to: 36, speed: 1.55 },  // 느리게
{ name: '대홀 진입', from: 92, to: 123, speed: 0.55 }, // 빠르게
```

현재 설정값입니다.

**main**

| 구간 | 프레임 | speed | 결과 |
| --- | --- | --- | --- |
| 동전 폭발 | 8–36 | 1.55 | 0.97x 보통 |
| 성 등장 | 45–79 | 1.55 | 0.98x 보통 |
| 대홀 진입 | 92–123 | 0.55 | 0.43x 빠르게 |
| 딜러 등장 | 124–144 | 2.40 | 1.43x 느리게 |
| 카드 딜링 | 145–179 | 1.65 | 1.13x 느리게 |
| 카드 뒤집기 | 180–203 | 3.00 | 1.79x 느리게 |
| 비행 | 213–263 | 1.45 | 0.92x 보통 |

비행은 51장으로 가장 긴 구간이라 자동 페이싱에 맡기면 프레임당 거리가 가장 짧은 축인데
그 속도가 오래 지속됐습니다. `speed` 를 주고 이동 거리를 함께 늘려, 다른 구간의 절대
속도는 그대로 두고 비행만 3.53vh/프레임으로 늦췄습니다.

**bridge**

| 구간 | 프레임 | speed | 결과 |
| --- | --- | --- | --- |
| 전환 | 0–21 | — | 1.00x |

한 구간뿐이라 speed 를 나눌 대상이 없습니다. 속도는 `--travel-bridge` 로 조절합니다.
양옆(비행 3.53 / 편대 비행 3.45)이 둘 다 평균보다 느린 컷이라 3.50vh 에 맞춰 두었습니다.

**ascent**

| 구간 | 프레임 | speed | 결과 |
| --- | --- | --- | --- |
| 편대 비행 | 0–6 | — | 0.90x |
| 폭발 | 7–31 | 1.50 | 1.17x 느리게 |
| 엔진 클로즈업 | 32–47 | — | 0.83x |
| 기체 전환 | 48–71 | 0.75 | 0.67x 빠르게 |
| 제트 점화 | 72–95 | 1.60 | 1.23x 느리게 |
| 노즐 클로즈업 | 96–111 | 1.20 | 0.98x |
| 제트 분사 | 112–127 | 0.90 | 0.82x 빠르게 |
| 우주 진입 | 128–143 | 1.80 | 1.30x 느리게 |

`speed` 는 **시퀀스 안에서의 상대값**입니다. 이동 거리(`--travel-*`)는 고정이라,
한 구간을 늘리면 같은 시퀀스의 나머지가 그만큼 줄어듭니다. 표의 "결과" 는 지정한 speed 를
그 시퀀스 평균으로 다시 환산한 값입니다. 모든 구간을 똑같이 1.5로 올리면 아무것도
변하지 않습니다. 시퀀스 **전체**를 느리게 하려면 `--travel-*` 를 늘리세요.

그래서 한 구간만 늦추고 싶을 때는 두 가지를 같이 해야 합니다. `speed` 를 올려 비중을 주고,
나머지 구간이 그만큼 빨라지지 않도록 `--travel-*` 를 같은 비율로 늘립니다.
`pace-profile.mjs` 로 손대지 않은 구간의 vh/프레임이 그대로인지 확인하면 됩니다.

경계에서 속도가 뚝 끊기면 스크롤이 걸리는 느낌이 나므로, `BLEND_RADIUS` 프레임에 걸쳐
완만하게 갈아탑니다.

### 반영하기

이미지는 그대로 두고 `pacing` 만 다시 계산합니다. 재인코딩이 없어 1초면 끝납니다.

```bash
cd blitzcrown-v2/.tools
bun run repacing.mjs           # 전체
bun run repacing.mjs ascent    # 한 시퀀스만
```

구간 경계를 새로 잡아야 하면 프레임 번호가 찍힌 썸네일 시트를 뽑아 확인하세요.

```bash
bun run contact-sheet.mjs          # main   → .tools/shots/sheet-main-*.png
bun run contact-sheet.mjs bridge   # bridge → .tools/shots/sheet-bridge-*.png
bun run contact-sheet.mjs ascent   # ascent → .tools/shots/sheet-ascent-*.png
```

페이싱을 바꾸면 같은 진행도가 다른 프레임을 가리키므로, 챕터 타이밍을 다시 잡아야 합니다.

```bash
bun run chapter-map.mjs
```

컷 전환 프레임 번호를 넣으면 `index.html` 에 써야 할 `data-start` / `data-end` 값을
계산해 줍니다. 스크립트 안의 `chapters` 배열을 새 영상 컷에 맞게 고친 뒤 실행하세요.

결과는 실제 브라우저에서 확인할 수 있습니다. (먼저 `bun run serve.mjs` 로 로컬 서버를 띄우세요)

```bash
bun run scan.mjs bridge    # 지점마다 몇 프레임이 지나갔는지 막대로 표시
bun run verify.mjs         # 전 구간 재생 + 구간 자 이음새(px) + 콘솔 오류
bun run mobile-check.mjs   # 390×844 뷰포트에서 같은 검증
```

## 샤프닝에 대해

현재 원본은 DOF와 모션블러가 강해 1920 해상도만큼의 디테일을 담고 있지 않습니다.
(절반으로 줄였다 되돌려도 차이가 거의 없습니다.) 그래서 변환 단계에서 언샤프 마스크를
한 번 겁니다. quality를 올리는 것보다 체감 개선이 훨씬 큽니다.

`sigma` 를 1.5 이상으로 올리면 머리카락·윤곽에 흰 테두리가 보이기 시작하니 주의하세요.
반대로 렌더 자체가 선명한 영상으로 교체한다면 `sharpen` 을 빼는 편이 자연스럽습니다.
